## 1. 배경 및 목적

### 1.1 배경

개인이 자신의 할 일을 기록하고 관리할 수 있는 웹 서비스가 필요하다.
기존 메모 앱은 할 일의 완료 여부·마감일·우선순위를 구조적으로 다루지 못하고,
설명을 서식 있는 형태로 남기기 어렵다.

### 1.2 목적

- 이메일 또는 구글 계정으로 가입해, **본인의 할 일만** 안전하게 관리할 수 있는 서비스를 제공한다.
- 할 일에 마감일·우선순위·서식 있는 상세 설명을 붙여 단순 체크리스트 이상의 맥락을 남긴다.
- 개인 프로젝트/학습 목적의 풀스택 구현이며, 1차 목표는 **로컬 환경에서 완결된 동작**이다.
- 상업적 운영 계획은 없다. 1단계 로컬 개발 완료 → 2단계 AWS 배포(이 문서 범위 밖) 순으로 진행한다.

### 1.3 기술 스택

이 절은 **스택 사실의 단일 출처**다. `docs/guides/` 의 모든 가이드가 이 표를 참조하며,
가이드의 서술이 이 표와 어긋나면 이 표를 따른다.

**설치 상태**는 실제 `todo-backend/pom.xml` · `todo-frontend/package.json` 기준이다.

## 2. 목표 및 성공 기준

| 목표                            | 성공 기준                                                                                    |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| G-1. 안전한 개인화된 할 일 관리 | 로그인한 사용자가 자신의 Todo만 조회·수정·삭제할 수 있고, 타인의 리소스 접근이 전부 차단된다 |
| G-2. 진입 장벽이 낮은 가입      | 이메일+비밀번호 또는 구글 계정만으로, 별도 인증 단계(메일 확인 등) 없이 가입할 수 있다       |
| G-3. 즉각적인 사용감            | 완료 토글·삭제가 서버 응답을 기다리지 않고 화면에 즉시 반영된다                              |
| G-4. 대량 데이터에서도 쾌적     | Todo가 늘어나도 목록 조회는 항상 한 페이지 분량만 가져온다                                   |
| G-5. 환경에 맞는 화면           | 라이트/다크 테마를 지원하고, 320px 모바일부터 데스크톱까지 레이아웃이 깨지지 않는다          |
| G-6. 삭제 데이터 보존           | 삭제된 데이터가 물리적으로 소실되지 않는다 (Soft Delete)                                     |

> G-6은 데이터 보존 자체를 목표로 한다. 사용자에게 노출되는 복구(휴지통) 화면은 이번 범위가 아니며 14장 후보다.

## 4. 범위

### 4.1 포함 (In Scope)

- 이메일/비밀번호 회원가입·로그인·로그아웃
- 구글 OAuth2 소셜 로그인 (백엔드 처리, 자체 JWT 발급)
- Todo 생성 / 목록 조회 / 상세 조회 / 수정 / 완료 토글 / 삭제
- 목록 페이지네이션, 완료 상태 필터, 키워드 검색
- Soft Delete
- Tiptap 리치 텍스트 에디터 (Todo 상세 설명 전용)
- 라이트/다크 테마 토글
- 반응형 레이아웃
- Swagger API 문서
- 통합 테스트

### 4.2 제외 (Out of Scope)

| 제외 항목                           | 사유                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| **카카오 등 구글 외 소셜 로그인**   | 1차는 구글 단일 소셜 로그인으로 한정. 확장 시 FR-A08 구현 패턴을 그대로 재사용 |
| Refresh Token, 자동 갱신            | 24시간 Access Token 단독으로 충분                                              |
| 비밀번호 찾기·재설정                | 1차 범위 밖                                                                    |
| 이메일 인증(가입 확인 메일)         | 1차 범위 밖                                                                    |
| 회원 탈퇴 UI                        | 스키마(`deleted_at`)만 준비, 화면은 미구현                                     |
| 정렬 옵션 UI                        | 최신순 고정. API의 `sort` 파라미터는 확장 대비용 (FR-T06)                      |

| 알림(푸시·이메일)                   | 해당 없음                                                                      |
| 다국어(i18n)                        | 한국어 단일                                                                    |
| AWS 배포 설정                       | 별도 단계                                                                      |
| Docker 컨테이너화                   | 사용하지 않기로 확정                                                           |

> 로그인 여부 판정은 클라이언트 측 토큰 검사가 아니라 `GET /api/auth/me` 응답으로 한다.
> `localStorage`/`sessionStorage`에 토큰을 보관하는 코드는 이 PRD 위반이다.

### 5.4 API 엔드포인트 개요

기능 요구사항에 대응하는 백엔드 계약의 **전체 목록**이다.
요청·응답 스키마와 예시는 `API_SPEC.md`를 따른다.

| Method | 경로                           | 설명                           | 인증 | 관련 FR          |
| ------ | ------------------------------ | ------------------------------ | ---- | ---------------- |
| POST   | `/api/auth/signup`             | 회원가입 (가입 즉시 쿠키 발급) | ❌   | FR-A01~A05, A12  |
| POST   | `/api/auth/login`              | 로그인, JWT 쿠키 발급          | ❌   | FR-A02, A03, A06 |

| GET    | `/api/todos`                   | 목록 — 페이지네이션·필터·검색  | ✅   | FR-T05~T08       |

| PATCH  | `/api/todos/{id}/toggle`       | 완료 토글                      | ✅   | FR-T10, T13      |

## 6. 사용자 여정 및 유저 스토리

### 6.0 전체 흐름

```
/ (랜딩)
 ├─ 로그인 상태  → /todos 로 리다이렉트
 └─ 비로그인     → [시작하기] → /login  ↔  /signup

/login ─ 이메일 로그인 ────────────→ /todos
       └ [구글로 계속하기] → 구글 동의 → /oauth2/callback ─┬─ 성공 → /todos
                                                           └─ 취소/실패 → /login?error=oauth

/todos ─ [새 할 일] ─────→ /todos/new ── 저장 ──→ /todos
       ├ 항목 클릭 ──────→ /todos/[id] ─ 수정/삭제 ─→ /todos
       └ 체크박스 클릭 ──→ 완료 토글 (페이지 이동 없음, 낙관적 업데이트)

보호된 경로(/todos*)에 미인증 접근 → /login 리다이렉트  (FR-A10)
타인 소유 /todos/[id] 접근          → 404 화면            (FR-T13)
```

### US-1. 회원가입

> 사용자로서, 이메일과 비밀번호로 계정을 만들어 내 할 일을 저장하고 싶다.

- [ ] 이메일 형식이 아니면 제출 전에 오류가 표시된다
- [ ] 비밀번호가 6자 미만이면 오류가 표시된다
- [ ] 중복 이메일이면 서버가 400과 안내 메시지를 반환하고 화면에 노출된다
- [ ] 성공 시 계정이 생성되고 JWT 쿠키가 발급되며 할 일 목록으로 이동한다
- [ ] DB의 password 컬럼이 BCrypt 해시다

### US-2. 로그인

> 사용자로서, 다시 방문했을 때 로그인해 내 할 일을 이어서 보고 싶다.

- [ ] 올바른 자격 증명이면 JWT 쿠키가 발급된다
- [ ] 비밀번호가 틀리면 "이메일 또는 비밀번호가 올바르지 않습니다" 수준의 메시지만 노출한다 (계정 존재 여부 미노출)
- [ ] 로그인 상태로 `/login` 접근 시 할 일 목록으로 보낸다
- [ ] 응답 본문에 토큰 값이 포함되지 않는다 (FR-A06)

### US-3. 구글 로그인

> 사용자로서, 비밀번호를 만들지 않고 구글 계정으로 바로 시작하고 싶다.

- [ ] "구글로 계속하기" 클릭 시 구글 동의 화면으로 이동한다
- [ ] 인증 후 서비스로 돌아오면 로그인 상태이고 할 일 목록이 보인다
- [ ] 처음이면 계정이 생성되고, 같은 이메일의 로컬 계정이 있으면 그 계정에 연결된다
- [ ] 사용자가 동의를 취소하면 로그인 페이지로 돌아오고 오류가 안내된다

### US-4. 할 일 생성

> 사용자로서, 해야 할 일을 빠르게 적어두고 싶다.

- [ ] 목록에서 [새 할 일]을 누르면 작성 화면으로 이동한다
- [ ] 제목만 입력해도 생성된다
- [ ] 제목이 비어 있으면 저장 버튼이 동작하지 않거나 오류가 표시된다
- [ ] 마감일·우선순위·상세 설명은 선택 입력이다
- [ ] 저장하면 목록으로 돌아오고, 생성한 항목이 최상단에 나타난다

### US-5. 할 일 목록 조회

> 사용자로서, 내 할 일을 한눈에 보고 원하는 항목을 찾고 싶다.

- [ ] 최신 생성순으로 10건씩 표시된다
- [ ] 페이지 이동 시 해당 페이지 데이터가 로드된다
- [ ] 완료/미완료 필터가 동작한다
- [ ] 키워드 검색이 제목과 설명 모두에 적용된다
- [ ] 결과가 없으면 빈 상태 화면이 나온다
- [ ] 다른 사용자의 할 일은 어떤 조건으로도 나타나지 않는다

### US-6. 완료 토글

> 사용자로서, 끝낸 일을 한 번의 클릭으로 표시하고 싶다.

- [ ] 클릭 즉시 체크 상태가 바뀐다 (서버 응답 대기 없음)
- [ ] 서버 요청이 실패하면 원래 상태로 되돌아가고 오류가 안내된다
- [ ] 목록에서 페이지 이동 없이 처리된다

### US-7. 할 일 상세 조회 및 수정

> 사용자로서, 할 일의 전체 내용을 보고 바뀐 부분을 고치고 싶다.

- [ ] 목록에서 항목을 클릭하면 상세 화면으로 이동한다
- [ ] 상세 설명의 서식(굵게·목록·인용 등)이 저장했던 그대로 렌더링된다
- [ ] 편집을 시작하면 기존 값이 모두 채워져 있다
- [ ] 저장 시 목록에 즉시 반영된다
- [ ] 다른 사용자의 할 일 주소로 직접 접근하면 404 화면이 나온다

### US-8. 할 일 삭제

> 사용자로서, 필요 없어진 할 일을 목록에서 치우고 싶다.

- [ ] 삭제 확인 절차가 있다
- [ ] 확인 시 목록에서 즉시 사라진다
- [ ] DB에는 행이 남고 `deleted_at`만 채워진다
- [ ] 삭제된 항목은 목록·검색·상세 조회 어디에서도 나오지 않는다

### US-9. 테마 전환

> 사용자로서, 어두운 환경에서도 눈이 편하게 쓰고 싶다.

- [ ] 헤더의 토글로 라이트/다크를 전환한다
- [ ] 새로고침 후에도 선택이 유지된다
- [ ] 두 테마 모두에서 텍스트 대비가 충분하다

| `/todos/[id]`      | 할 일 상세·편집 | 로그인 + 본인 소유 | 서식 있는 설명 렌더링, 편집 폼(Tiptap), 삭제 버튼                                         | FR-T05, T09, T11, T13          |
| `/oauth2/callback` | 리다이렉트 경유 | 전체               | 로딩 표시 후 목적지로 이동. 성공 → `/todos`, 실패 → `/login?error=oauth`                  | FR-A08, A09                    |

**공통 헤더**: 로고 / 테마 토글(FR-U01) / 로그인 상태별 메뉴 — 로그아웃(FR-A07) 또는 로그인·회원가입

**전 화면 공통 적용**: FR-U02(반응형), FR-U07(애니메이션), FR-U08(키보드·포커스)는 특정 화면이 아니라 모든 화면에 적용된다.
FR-A12(탈퇴 이메일 재가입)는 탈퇴 UI가 없어 대응 화면이 없으며, 통합 테스트로만 검증한다 (5.1 참조).

> **`/oauth2/callback`은 토큰을 받아 저장하는 화면이 아니다.**
> 백엔드 `OAuth2SuccessHandler`가 이미 httpOnly 쿠키를 심은 뒤 이 경로로 리다이렉트하므로,
> 이 화면은 목적지로 넘기는 역할만 한다 (FR-A06 인증 토큰 취급 원칙).

> **랜딩(`/`)의 리다이렉트 판정을 클라이언트에서 토큰을 읽어 처리하지 않는다.**
> httpOnly 쿠키는 자바스크립트로 읽을 수 없다. 서버 사이드에서 쿠키 존재를 확인하거나
> `GET /api/auth/me` 결과로 판정한다 (FR-A11).

## 8. 데이터 요구사항

### 8.1 제품 관점의 제약

| 항목       | 제약                                                                 |
| ---------- | -------------------------------------------------------------------- |
| 이메일     | 유효한 형식, 활성 계정 내에서 유일. 탈퇴 계정은 유일성 판정에서 제외 |
| 비밀번호   | 6자 이상. 소셜 가입자는 없을 수 있음                                 |
| 닉네임     | 필수, 최대 50자                                                      |
| 할 일 제목 | 필수, 최대 200자                                                     |
| 할 일 설명 | 선택, 서식 있는 텍스트. 저장 전 서버에서 위험 태그 제거              |
| 마감일     | 선택. 과거 날짜도 허용(이미 지난 일을 기록할 수 있어야 함)           |
| 우선순위   | 높음 / 보통 / 낮음, 기본 보통                                        |
| 삭제       | 물리 삭제 금지. `deleted_at` 기록                                    |

### 8.2 엔티티 및 필드

모든 엔티티는 `id`(BIGINT, auto)와 `created_at` · `updated_at` · `deleted_at` 공통 필드를 가진다.
조회는 항상 `deleted_at IS NULL` 조건을 포함한다 (Soft Delete).

#### User — 사용자 계정

| 필드         | 설명                               | 타입 / 제약                                  |
| ------------ | ---------------------------------- | -------------------------------------------- |
| `id`         | 고유 식별자                        | BIGINT, PK, auto                             |
| `email`      | 로그인 ID                          | VARCHAR, **활성 계정 내 유일** (부분 유니크) |
| `password`   | BCrypt 해시                        | VARCHAR, **nullable** (소셜 가입자는 NULL)   |
| `nickname`   | 표시 이름                          | VARCHAR(50), NOT NULL                        |
| `provider`   | 가입 경로                          | ENUM(`LOCAL`, `GOOGLE`), NOT NULL            |
| `role`       | 권한 (확장 대비, 이번 범위 미사용) | ENUM, 기본 `USER`                            |
| `created_at` | 생성일시                           | TIMESTAMP                                    |
| `updated_at` | 수정일시                           | TIMESTAMP                                    |
| `deleted_at` | Soft Delete 시각                   | TIMESTAMP, nullable                          |

> **부분 유니크 인덱스**: `UNIQUE (email) WHERE deleted_at IS NULL`
> 탈퇴한 계정의 이메일은 유일성 판정에서 제외되어 재가입이 가능하다 (FR-A12).
> 일반 UNIQUE 제약으로는 이 요구사항을 만족할 수 없다.

#### Todo — 할 일

| 필드          | 설명                       | 타입 / 제약                                     |
| ------------- | -------------------------- | ----------------------------------------------- |
| `id`          | 고유 식별자                | BIGINT, PK, auto                                |
| `user_id`     | 소유자                     | BIGINT, FK → `User.id`, NOT NULL, **LAZY 연관** |
| `title`       | 제목                       | VARCHAR(200), NOT NULL                          |
| `description` | 상세 설명 (서식 있는 HTML) | TEXT, nullable, **저장 전 서버 sanitize**       |
| `due_date`    | 마감일                     | DATE, nullable (과거 날짜 허용)                 |
| `priority`    | 우선순위                   | ENUM(`HIGH`, `MEDIUM`, `LOW`), 기본 `MEDIUM`    |
| `completed`   | 완료 여부                  | BOOLEAN, NOT NULL, 기본 `false`                 |
| `created_at`  | 생성일시                   | TIMESTAMP                                       |
| `updated_at`  | 수정일시                   | TIMESTAMP                                       |
| `deleted_at`  | Soft Delete 시각           | TIMESTAMP, nullable                             |

> **인덱스**: `(user_id, deleted_at)`, `(user_id, completed, deleted_at)`
> 모든 목록 조회가 `user_id` + `deleted_at IS NULL`로 시작하므로 이 조합이 선행 컬럼이어야 한다 (NFR-P02).

### 8.3 스키마 표기 규칙

데이터베이스명은 `postgres`, **스키마명은 `todolist_db`(전부 소문자)로 통일**한다.
PostgreSQL은 따옴표 없는 식별자를 소문자로 접기 때문에, `TodoListDB`·`Todolist_db` 같은
혼합 대소문자 표기를 설정 파일·DDL·문서 어디에도 쓰지 않는다.

## 9. 비기능 요구사항

### 9.1 보안 (NFR-S)

| ID      | 요구사항                                                                                                                                |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-S01 | 비밀번호는 BCrypt로 해시한다. 어떤 경로로도 평문이 저장·전송·로깅되지 않는다                                                            |
| NFR-S02 | JWT는 httpOnly 쿠키로만 전달한다. 응답 본문에 토큰을 담지 않으며, 자바스크립트가 토큰을 읽거나 저장하지 않는다                          |
| NFR-S03 | JWT 시크릿·구글 클라이언트 시크릿·DB 비밀번호는 환경변수 또는 `.gitignore` 처리된 로컬 설정 파일로만 주입한다. 저장소에 커밋하지 않는다 |
| NFR-S04 | 모든 API 요청 본문은 서버에서 검증한다. 프론트 검증에 의존하지 않는다                                                                   |
| NFR-S05 | 리치 텍스트 설명은 서버에서 sanitize한다. `script`·이벤트 핸들러 속성이 저장되지 않는다                                                 |
| NFR-S06 | 모든 Todo 접근에 소유권을 검증한다. 검증 실패 시 리소스 존재 여부를 노출하지 않는다                                                     |
| NFR-S07 | 에러 응답에 스택트레이스·내부 예외 메시지·SQL을 노출하지 않는다                                                                         |
| NFR-S08 | CORS는 허용 출처를 명시한다. 와일드카드를 쓰지 않으며 `allowCredentials`를 켠다                                                         |

### 9.2 성능 (NFR-P)

## 10. 에러 처리 정책

| 상황                        | HTTP | 사용자에게 보이는 메시지 방향                                            |
| --------------------------- | ---- | ------------------------------------------------------------------------ |
| 입력값 검증 실패            | 400  | 어떤 필드가 왜 잘못됐는지 필드 옆에 표시                                 |
| 이메일 중복                 | 400  | "이미 사용 중인 이메일입니다"                                            |
| 로그인 실패                 | 401  | "이메일 또는 비밀번호가 올바르지 않습니다" (어느 쪽이 틀렸는지 미노출)   |
| 미인증 접근                 | 401  | 로그인 페이지로 이동                                                     |
| 존재하지 않거나 남의 리소스 | 404  | "요청하신 할 일을 찾을 수 없습니다"                                      |
| 서버 오류                   | 500  | "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해 주세요" + 재시도 버튼 |

에러 응답 형식과 에러 코드 목록은 `API_SPEC.md`를 따른다 (NFR-M02).
