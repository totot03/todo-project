# PRD.md 점검 및 정합화

## Context

`docs/PRD.md`(v1.0, 2026-08-26)는 요구사항 ID 체계(FR-A/FR-T/FR-U, NFR-S/P/U/M)와 유저 스토리·수용 기준을 갖춘 완성도 높은 문서다. 불변 규칙 6종(이메일 전용 로그인 · 비밀번호 6자 · JWT 24h · Soft Delete · 페이지네이션 · 소유권 검증)은 **전부 정확히 반영**되어 있고, 에러 처리 정책(10장)과 릴리스 체크리스트(12장)까지 갖춘 보기 드문 수준이다.

문제는 내용의 품질이 아니라 **참조 무결성**과 **스코프 경계 문서화**다. M0 착수 직전 시점에 세 갈래 결함이 확인됐다.

1. **위임한 곳이 비어 있다.** PRD는 "무엇을·왜"만 다루고 "어떻게"를 `CLAUDE.md`(루트)에, 실행 계획을 `PHASE_PROMPTS.md`에 위임했으나 **두 파일 모두 존재하지 않는다**. 그 결과 8장이 넘긴 **데이터 모델이 어느 문서에도 없다**. 반대로 `docs/guides/*` 3개 파일은 `PRD.md#13-기술-스택`을 "스택 사실의 단일 출처"로 인용하는데 **PRD 1.3은 "프로젝트 성격"이다 — 이미 깨진 앵커**.
2. **문서 3종이 서로 다른 UI를 가정한다.** PRD 7장은 화면 4개, `project-structure.md`는 7개, ROADMAP M5는 "인라인 또는 다이얼로그 수정"을 전제한다. 게다가 가이드의 인증 패턴(`saveToken`, `accessToken`, `토큰 유무로 리다이렉트`)은 PRD가 확정한 **httpOnly 쿠키 방식과 정면으로 모순**된다.
3. **범위 경계가 문서화되지 않은 축소·확장이 있다.** 카카오 로그인 제외(미기재), 정렬 파라미터(FR 없이 API에만 존재), FR-A12(트리거 경로 없음).

**목표**: PRD.md를 외부 문서 없이 자립 가능한 단일 출처로 만들고, 깨진 앵커를 복구하며, 화면·API·데이터 모델의 갭을 메워 M0 착수 가능 상태로 만든다.

## 사용자 확정 사항

- **참조 문서**: PRD 자립 + `docs/API_SPEC.md`만 신설. `CLAUDE.md`·`PHASE_PROMPTS.md`는 만들지 않고 참조를 실존 문서로 대체.
- **범위**: 감사 보고 + `docs/PRD.md` 수정. `ROADMAP.md`·`docs/guides/*`는 **수정하지 않고** 불일치 목록만 보고.

### 2. **1.3절을 "기술 스택"으로 교체** ⭐ 앵커 복구

`docs/guides/*` 3개 파일이 `#13-기술-스택` 앵커를 참조하므로, **새 절을 만들지 말고 1.3 자체를 기술 스택으로 바꾼다.** 이렇게 하면 guides 파일을 한 줄도 건드리지 않고 깨진 링크 3건이 동시에 복구된다 (사용자가 확정한 "PRD.md만 수정" 범위와 정확히 일치).

기존 1.3 "프로젝트 성격"의 두 줄은 1.2(목적)의 마지막 항목으로 흡수한다.

표에는 **설치 상태 열**을 둔다 — guides가 "설치 상태를 먼저 확인하라"고 안내하는데 그 정보가 어디에도 없었다. 값은 실제 `pom.xml`/`package.json` 기준:

- 설치됨: Spring Boot 4.1.1, JDK 21, Next.js 16.3.3, React 19.2.8, Tailwind v4, radix-ui, jjwt 0.12.6
- **미설치(M4~M5 도입 예정)**: TanStack Query, Framer Motion, Tiptap, next-themes, React Hook Form, Zod

### 3. 화면 정의(7장) 갭 해소 — **별도 페이지로 확정** ✅ 사용자 결정

세 문서가 서로 다른 UI를 가정하던 것을 `project-structure.md` 쪽으로 통일한다. PRD 7장 표를 4행 → **7행**으로 확장:

| 경로               | 화면            | 접근 권한            | 주요 요소                                                  |
| ------------------ | --------------- | -------------------- | ---------------------------------------------------------- |
| `/`                | 랜딩            | 전체                 | 서비스 소개, 시작하기. 로그인 상태면 `/todos`로 리다이렉트 |
| `/login`           | 로그인          | 비로그인             | 이메일·비밀번호 폼, 구글 버튼, 회원가입 링크               |
| `/signup`          | 회원가입        | 비로그인             | 이메일·비밀번호·닉네임 폼, 구글 버튼, 로그인 링크          |
| `/todos`           | 할 일 목록      | 로그인 필수          | 필터, 검색, 목록, 페이지네이션, 작성 버튼                  |
| `/todos/new`       | 할 일 작성      | 로그인 필수          | 제목·마감일·우선순위·Tiptap 설명                           |
| `/todos/[id]`      | 상세·편집       | 본인 소유만 (FR-T13) | 서식 설명 렌더, 편집, 삭제                                 |
| `/oauth2/callback` | 리다이렉트 경유 | 전체                 | 성공 → `/todos`, 실패 → `/login?error=oauth`               |

**근거**: Tiptap 에디터가 들어가는 폼은 목록에 인라인으로 넣기엔 무겁고, `[id]` URL이 있어야 FR-T13(타인 리소스 404)을 URL 레벨에서 검증할 수 있다.

**파생 수정**: `/todos`의 주요 요소에서 "생성 폼"을 빼고 "작성 버튼"으로 교체 (현행 PRD L246은 `/todos`에 생성 폼이 있다고 서술).

`/oauth2/callback`은 **"토큰 수신"이 아니라 "리다이렉트 경유"**로 서술한다 — 쿠키는 백엔드 `OAuth2SuccessHandler`가 이미 심었으므로 이 페이지는 목적지로 넘기는 역할만 한다 (`project-structure.md:55`의 "토큰 수신" 표현은 httpOnly 쿠키 설계와 모순).

**충돌 보고 대상**: `ROADMAP.md:244` M5 "수정(인라인 또는 다이얼로그)" — 이 결정과 어긋나므로 사용자에게 보고.

### 4. 인증 방식 모순 차단 — FR-A06 / NFR-S02 보강

가이드 문서의 `saveToken`·`lib/auth/token.ts`·"토큰 유무로 리다이렉트"·"JWT 자동첨부" 패턴이 틀렸다는 **근거를 PRD에 명문화**한다:

> 로그인·회원가입 응답 바디에 토큰 값을 포함하지 않는다. 프론트엔드는 토큰을 저장·조회하지 않으며, 인증 상태는 `GET /api/auth/me` 호출로만 판정한다. API 호출은 `credentials: "include"`로 쿠키를 자동 전송한다.

- 에러 코드 표 — PRD 10장 에러 처리 정책과 1:1 대응
- 인증: `Authorization` 헤더가 아니라 **httpOnly 쿠키** 전제임을 서두에 명시
